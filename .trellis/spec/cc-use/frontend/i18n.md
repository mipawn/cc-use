# Internationalization (i18n)

> Two locale files, one namespace tree, and a strict rule: user-facing strings exist in both languages before the change is done.

---

## Setup

`src/renderer/locales/index.ts` initializes i18next once:

- resources: `en: { translation: en }`, `zh: { translation: zh }` (default exports of `en.ts` / `zh.ts`);
- `lng`: `localStorage.getItem('language') ?? 'zh'` — Chinese is the product default;
- `fallbackLng: 'zh'`;
- `interpolation.escapeValue: false`.

`main.tsx` imports `./locales` for the side effect and keeps antd/dayjs in sync: `ConfigProvider locale={isChinese ? zhCN : enUS}`, dayjs `zh-cn`/`en` in an effect (`main.tsx`). `settingsStore.setLanguage()` persists to `localStorage` and calls `i18n.changeLanguage()`.

---

## Key Rules

1. **Every user-facing string goes in `src/renderer/locales/zh.ts` and `src/renderer/locales/en.ts` in the same change.** `CONTRIBUTING.md` states this; the pre-commit checklist repeats it.
2. **Group keys by page/module, not by component.** Top-level groups currently are:
   `workspace`, `sidebar`, `launchpad`, `integrations`, `common`, `settings`, `console`, `instances`, `dashboard`, `providers`, `projects`, `newProject`, `dropZone`, `messages`, `apiKeys`, `keys`, `keyDetail`, `keyCascader`, `configPreview`, `statistics`, `usageDetail`, `globalConfig`, `terminalTools`, `migration`, `sessions`.
   Use `common.*` for reusable words (`common.save`, `common.cancel`, `common.delete`, `common.retry`, `common.noData`, `common.nothingToRefresh`). Nest for sub-domains, e.g. `statistics.granularity.day` (`locales/zh.ts:870-874`).
3. **Interpolation uses i18next double-brace syntax** (`{{version}}`, `{{count}}`, …) passed as the second argument:
   - `t('settings.newVersionDesc', { version: updateInfo.version })` — `App.tsx:79-84`
   - `t('instances.exitCode', { code: record.exitCode })` — `pages/Instances.tsx:298`
   - `t('providers.usageWindowUsed', { percent: formatUsedPercent(...) })` — `components/providers/ProviderUsageWindows.tsx`
   - `t('sessions.sessionCount', { count: filteredSessions.length })` — `sessions.sessionCount: '{{count}} 个会话'` / `'{{count}} sessions'`.
4. **Use `useTranslation()` in components** (`const { t } = useTranslation()`), then `t('settings.xxx')`. Outside React (stores, plain helpers) use the default `i18n` export or pass `t` in:
   - `stores/settingsStore.ts` uses `i18n.t('settings.fetchFailed')` in error toasts;
   - `utils/accountQuery.ts` exposes `usageWindowLabel(window, t)` so labels stay translatable without importing React.
5. **Format numbers/dates by language, not by hardcoded Chinese/English.** Take the active language from `i18n.resolvedLanguage || i18n.language` and pass it to formatters: `formatTokenCount(value, language)` (`utils/formatTokens.ts`, used by `pages/Dashboard.tsx:32`, `components/usage/*`), `new Intl.DateTimeFormat(i18n.language.startsWith('zh') ? 'zh-CN' : 'en-US', ...)` (`components/dashboard/UsageHeatmap.tsx:175`).
6. **Never write user-visible literals in JSX or `message.*` calls** in new code. Localized copy comes from `t()`, and missing keys are a bug to fix in the locales, not to paper over with a literal.

## Current Drift (fix when you touch these areas)

`zh.ts` and `en.ts` are **not** in full sync. Measured from the two default exports: 928 Chinese keys vs 920 English keys.

- Missing in `en.ts` (11): `common.show` / `common.hide` / `common.status`, `settings.selectDefaultKey`, `settings.defaultTerminal`, `dashboard.dropToLaunch` / `dashboard.startingProxy` / `dashboard.proxyStartFailed`, `configPreview.selectKeyFirst`, and two `keyCascader` hint keys (an input-hint key plus `keyCascader.noKeys`).
- Missing in `zh.ts` (3): `dashboard.selectKeyHint`, `dashboard.envPreview`, and one `settings` default-key hint key. The parity snippet below prints the exact key names.
- Because `fallbackLng: 'zh'`, an English UI falls back to Chinese for the 11 keys missing from `en.ts`; the 3 keys missing from `zh.ts` show the raw key string in the Chinese UI (English users see the English value).

Refresh the comparison after edits (works from the repo root, reads the locale modules with Node's `vm`, no build step):

```bash
node -e "
const fs=require('fs'),vm=require('vm');
const load=p=>{const m={exports:{}};vm.runInNewContext(fs.readFileSync(p,'utf8').replace('export default','module.exports ='),{module:m,exports:m.exports});return m.exports};
const flat=(o,p='')=>Object.keys(o).reduce((r,k)=>{const v=o[k],key=p?p+'.'+k:k;return r.concat(v&&typeof v==='object'&&!Array.isArray(v)?flat(v,key):[key])},[]);
const zh=new Set(flat(load('src/renderer/locales/zh.ts'))), en=new Set(flat(load('src/renderer/locales/en.ts')));
console.log('missing in en:',[...zh].filter(k=>!en.has(k)));
console.log('missing in zh:',[...en].filter(k=>!zh.has(k)));
"
```

Do not add new `t('some.key') || '中文 fallback'` expressions. When a key is missing, i18next returns the key string itself, which is truthy, so the `||` branch never runs — this pattern already litters `Settings.tsx`, `Keys.tsx`, `Console.tsx`, `ClaudeCodePage.tsx`. Add the key to both locale files instead.

## Tests

`src/renderer/locales/usageChartLocales.test.ts` imports `en.ts` and `zh.ts` directly and asserts (a) that specific chart keys exist in both languages and (b) that the Chinese values are actually translated. It is the existing safety net for locale edits; extend the same style when adding a new group of keys, or add a key-parity test using the comparison above.

---

## Checklist for a Text Change

- [ ] Key added to `zh.ts` and `en.ts`, grouped under the right page/module.
- [ ] Key reused from `common.*` rather than duplicated.
- [ ] Interpolation variables named and passed on both call sites.
- [ ] Both files still parse (`pnpm tsc --noEmit` catches locale syntax errors because both are typed modules).
- [ ] Parity check above shows no new gaps.
- [ ] No literal user-facing string added to `.tsx`.
